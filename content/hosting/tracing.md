The CMS records requests as [OpenTelemetry](https://opentelemetry.io) traces, the standard that
Datadog, Grafana, Honeycomb and New Relic read. The [Performance plugin](/documentation/performance)
shows them to administrators, and plugins can read them; see the Plugin Handbook's
[Tracing](/plugins/tracing).

## How it's set up

`cms generate` writes `src/instrumentation.ts`, which Next.js loads once when the server starts:

```ts
// @generated by `cms generate`. Edits are overwritten; delete this line to keep yours.
export { register } from '@otwdesign/next/instrumentation'
```

It installs an OpenTelemetry tracer that records nothing until an active plugin calls
`cms.traces.enable()`. There's nothing to configure.

## What it costs

Measured on a shop page that takes 4.2 ms to serve, 400 requests each:

| Situation                                            | Extra time per request |
| ---------------------------------------------------- | ---------------------- |
| No plugin records requests                           | about 0.08 ms          |
| A plugin records them, and drops a visitor's request | about 0.15 ms          |
| An administrator viewing the performance bar         | about 0.6 ms           |

Recorded requests are held in memory until they end; kept ones (at most 100) for ten minutes.

## Next.js's spans

Next.js records its own steps too: routing, rendering, `generateMetadata`. Set
`NEXT_OTEL_VERBOSE=1` for more of them.

## A site's own OpenTelemetry

A site that already sets up OpenTelemetry, for Sentry or an APM, keeps its `instrumentation.ts`:
`cms generate` leaves a file without the `@generated` line alone. Add the CMS's span processor to
the site's tracer provider, and the CMS's traces work alongside the site's exporter.

Next.js compiles `instrumentation.ts` for the Edge runtime as well as Node.js, so the setup goes
in a file of its own that only Node.js loads. Anything `instrumentation.ts` imports at the top
ends up in the Edge build too, and `@otwdesign/next/tracing` is Node.js only.

```ts filename="src/instrumentation.ts"
export async function register() {
  if (process.env.NEXT_RUNTIME === 'nodejs') await import('./instrumentation.node')
}
```

```ts filename="src/instrumentation.node.ts"
import { context, trace } from '@opentelemetry/api'
import { AsyncLocalStorageContextManager } from '@opentelemetry/context-async-hooks'
import { OTLPTraceExporter } from '@opentelemetry/exporter-trace-otlp-http'
import { BatchSpanProcessor, TracerProvider } from '@opentelemetry/sdk-trace'
import { cmsTracing } from '@otwdesign/next/tracing'

const cms = cmsTracing()
trace.setGlobalTracerProvider(
  new TracerProvider({
    spanProcessors: [
      cms.spanProcessor,
      new BatchSpanProcessor({ exporter: new OTLPTraceExporter() }),
    ],
  }),
)
// Without a context manager, spans don't nest: each would be a request of its own.
context.setGlobalContextManager(new AsyncLocalStorageContextManager())
```

The CMS is built on version 2 of the OpenTelemetry JavaScript SDK (`@opentelemetry/sdk-trace`
2.x, with the OTLP exporters numbered 0.2xx); use the same major version in the site.

With the site's own sampler, as above, every request is recorded and exported. Pass
`sampler: cms.sampler` to record only while a plugin has enabled tracing.

The CMS's own setup registers no propagator, so it ignores a `traceparent` header on incoming
requests: every request is recorded as its own, and only when a plugin wants it. A site that
registers one for distributed tracing makes a request that arrives with the header part of the
caller's trace; the performance bar then has no server trace for it.

Without the processor, the performance bar shows only the browser's numbers, and says that server
tracing is off.

## Several servers

Traces are kept in each server's memory. With several servers behind a load balancer, the bar's
request for a trace can reach a server other than the one that served the page. Send the
traces to an APM with an exporter, as above, to see them all in one place.
